# Plan d'implémentation — 07 A1, première ouverture

> **Pour les agents :** SOUS-COMPÉTENCE REQUISE — utiliser superpowers:subagent-driven-development
> (recommandé) ou superpowers:executing-plans pour dérouler ce plan tâche par tâche.
> Les étapes utilisent des cases à cocher (`- [ ]`) pour le suivi.

**Objectif :** l'écran d'accueil, fidèle au mockup, avec `⌘N` capté et inerte.

**Architecture :** quatre composants indépendants — `TitleBar`, `StatusBar`,
`ProjectSidebar`, `WelcomeHero` — assemblés par `WelcomeScreen`. Chacun ne lit que des
tokens et ne connaît que ses props. Un unique `onNewProject` remonte à `App`.

**Stack :** React · CSS Modules · Vitest · Playwright

**Spec :** `specs/07-a1-accueil.md` — **Prérequis :** plans `01` et `02` terminés

---

## Deux décisions techniques à connaître avant de commencer

**La barre de titre doit être déplaçable.** Avec `titleBarStyle: Overlay`, macOS ne
fournit plus de zone de glissement : sans `data-tauri-drag-region` sur la barre, la
fenêtre devient immobile. Tauri ne rend glissables que les éléments **portant**
l'attribut, donc les boutons enfants restent cliquables sans traitement particulier.

**La version vient du build, pas de l'IPC.** `getVersion()` de `@tauri-apps/api`
échouerait sous Playwright, qui exécute l'app dans Chromium sans runtime Tauri, et
rendrait les captures non déterministes. On injecte donc la version à la compilation.

- [ ] **Étape 1 : écrire le test qui échoue**

```tsx
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { WelcomeScreen } from './WelcomeScreen'

test('les deux boutons appellent le même callback', async () => {
  const onNewProject = vi.fn()
  render(<WelcomeScreen onNewProject={onNewProject} />)
  const boutons = screen.getAllByRole('button', { name: /nouveau projet/i })
  expect(boutons).toHaveLength(2)
  for (const b of boutons) await userEvent.click(b)
  expect(onNewProject).toHaveBeenCalledTimes(2)
})

test('⌘N appelle le callback', async () => {
  const onNewProject = vi.fn()
  render(<WelcomeScreen onNewProject={onNewProject} />)
  await userEvent.keyboard('{Meta>}n{/Meta}')
  expect(onNewProject).toHaveBeenCalledOnce()
})

test('n appelé seul ne déclenche rien', async () => {
  const onNewProject = vi.fn()
  render(<WelcomeScreen onNewProject={onNewProject} />)
  await userEvent.keyboard('n')
  expect(onNewProject).not.toHaveBeenCalled()
})
```

## Tâche 7 : capture de référence

**Fichiers :** créer `e2e/a1.spec.ts` ; modifier `.github/workflows/ci.yml`

La capture est prise dans Chromium via `pnpm dev`, pas dans WKWebView. Elle détecte
donc les **régressions**, pas les écarts absolus de rendu — ceux-là se jugent à l'œil
en tâche 8, dans l'app réelle.

- [ ] **Étape 1 : écrire le test**

```ts
import { expect, test } from '@playwright/test'

test('A1 est conforme à la référence', async ({ page }) => {
  await page.goto('/')
  await page.evaluate(() => document.fonts.ready)
  await expect(page).toHaveScreenshot('a1-accueil.png', { fullPage: true })
})
```

L'attente de `document.fonts.ready` est indispensable : sans elle la capture peut
tomber avant que les trois polices soient appliquées, et la référence serait instable.

- [ ] **Étape 2 : produire la référence, puis la relire**

```bash
pnpm test:e2e --update-snapshots
open e2e/a1.spec.ts-snapshots/
```

**Regarder l'image avant de la commiter.** Une référence fausse figerait le défaut.

Et surtout : **générer la référence là où elle sera vérifiée.** La tolérance est réglée à
`maxDiffPixelRatio: 0`, délibérément. Le rendu des polices variant d'une machine à
l'autre, une référence produite en local échouera en CI. Si l'écart apparaît, la bonne
réponse est de régénérer la référence dans la CI — la mauvaise est de relâcher la
tolérance, qui est précisément ce qui donne sa valeur au garde-fou. Concrètement :
committer la référence produite par la CI, pas celle de la machine de développement.

- [ ] **Étape 3 : vérifier qu'elle est stable**

```bash
pnpm test:e2e && pnpm test:e2e
```

Attendu : deux passages verts d'affilée.

- [ ] **Étape 4 : brancher la CI**

Ajouter dans `.github/workflows/ci.yml`, après `pnpm test` :

```yaml
      - run: pnpm exec playwright install --with-deps chromium
      - run: pnpm test:e2e
        env:
          CI: true
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report
          path: playwright-report/
```

L'artefact en cas d'échec est ce qui rend une régression visuelle diagnosticable sans
reproduire en local.

Profiter de ce passage pour revoir `playwright.config.ts` sur deux points laissés en
suspens au plan `01` : `reuseExistingServer` est câblé à `true`, ce qui en CI pourrait
faire servir une build obsolète par un serveur résiduel — le conditionner à l'absence de
`CI` ; et il n'y a ni `forbidOnly` ni `retries`, dont un `test.only` oublié qui passerait
la CI en silence.

